## 1. 定位与分期

| 阶段 | 形态 | 说明 |
|---|---|---|
| P0 | 规则版纯模板日报 | **零 LLM**，只跑通数据链路（步骤 1-6 + 模板拼装），先验证六步数据的可得性与质量 |
| P1 | LLM 叙事日报 | 在 P0 的结构化结果上，LLM 仅负责成稿润色（§3 步骤 7） |
| P2 | 根因提示增强 | 异常项挂接根因分析工具链（复用场景 1 的调用链），日报从"报异常"升级为"给线索" |

## 2. 触发与运行形态

- **触发**：编排层 cron（建议每日 09:00，覆盖前一自然日 00:00-24:00），不进 bingops 平台内；
- **运行单元**：一次日报 = 一次 agent 运行，全程只读（唯一可选写：归档工单）；
- **核心红线：规则引擎先算数，LLM 只写叙事**——所有数字来自确定性计算（步骤 6），
  LLM 不产出任何数字，这是防幻觉的关键。

```
cron 09:00
   │
   ▼
① 拉对象清单          bingops-mcp: list_business_apps（按团队分组）
   │
   ▼
② 展开检查项          bingops-mcp: get_app_overview → 每应用资源清单
   │                   → 按资源类别映射检查项（§3.2 检查项矩阵）
   ▼
③ 并行拉指标          prometheus-mcp: 过去 24h / 5m 步长 → avg/max/p95
   │
   ├───④ 告警统计─── n9e-mcp: 24h 事件按应用/级别聚合，未恢复单列
   │
   └───⑤ 变更摘要─── bingops-mcp: list_job_executions + list_tickets(change)
   │
   ▼
⑥ 异常判定            规则计算（§4）→ 结构化异常列表
   │
   ▼
⑦ 报告生成            结构化 JSON → (P1 起) LLM 按模板成稿
   │
   ▼
⑧ 输出                飞书 webhook 推送 + 可选建 general 工单归档
```

## 3. 执行流程细则

### 3.1 对象与检查项（步骤 1-2）

- 对象清单 = `list_business_apps`（team 分组），无 app 标签的资源归入"未归集"段落输出
  （本身就是治理信号，与场景 6 的无主资源清单同源）；
- **检查项矩阵起步放 agent 侧配置文件**（YAML：应用/模型 code → 检查项列表），
  P2 再考虑入平台表；不追求首轮配置化，避免阻塞。

### 3.2 指标映射（步骤 3）

| 资源类别 | PromQL 来源 |
|---|---|
| 主机（ECS/EC2/GCE） | node_exporter（label 与 SD 端点同源——采集 target 由平台 CMDB 快照生成，标识天然对齐） |
| Pod/容器 | container 指标（cluster/namespace/pod 标签对齐 CMDB k8s 层级） |
| RDS/Redis | 云监控/厂商导出器 |

- 窗口：过去 24h，5m 步长，聚合 avg/max/p95 三值；
- 每应用并行拉取，单应用失败隔离（§6）。

### 3.3 告警与变更（步骤 4-5）

- 夜莺：24h 事件按 应用/severity 聚合；**未恢复事件单独列示**并在总览计数；
- 变更摘要：`list_job_executions` + `list_tickets(type=change)` 过去 24h，
  每应用输出"昨日变更"段（含 tag、环境、执行人、结果）。

## 4. 异常判定规则（步骤 6）

规则先于 LLM 执行，输出结构化异常列表（应用、资源、指标、观测值、阈值、持续时长、证据链接）：

| 规则 | 默认阈值 | 级别 |
|---|---|---|
| CPU 持续高水位 | >80% 持续 ≥30min | warning |
| 磁盘使用率 | >85%（>95% 升 critical） | warning/critical |
| 内存使用率 | >90% 持续 ≥30min | warning |
| 服务错误率 | >5xx 阈值（按应用配置） | critical |
| Pod 重启 | 24h 内重启 ≥3 次 | warning |
| 告警未恢复 | 当前处于 firing | 按夜莺级别 |
| 变更异常 | 昨日 jobs 执行失败 | warning |

- 阈值全部可配置（agent 侧 YAML），首轮用默认值；
- 观测值必须附**证据链接**（Prometheus 图表 URL / 夜莺事件 URL / 工单号），LLM 不得省略或改写。

## 5. 报告模板（步骤 7）

结构化 JSON（规则产物）→ P1 起 LLM 按固定大纲成稿：

```
【XX 团队巡检日报 YYYY-MM-DD】
一、总览：巡检应用 N 个 / 异常 M 项 / 未恢复告警 K 条 / 昨日变更 X 次
二、异常项（按 critical → warning 排序，每条附证据链接）
三、风险提示（趋势类：磁盘增长、内存爬升等未达阈值但需关注项）
四、昨日变更回顾（按应用：tag、环境、结果）
五、待办建议（数据缺失补采、无 app 标签资源归集等治理项）
```

## 6. 容错与成本控制

| 机制 | 规则 |
|---|---|
| 应用级隔离 | 单应用指标/告警拉取失败 → 该应用标记"数据缺失"，其余照常出报；**绝不因个别应用中断整报** |
| 空数据语义 | 无数据的应用写"无数据"，禁止 LLM 编造 |
| 超时预算 | 单应用指标查询设超时；整报生成设全局 deadline，超时输出已完成部分+缺失声明 |
| token 控制 | 健康应用只传一行摘要给 LLM；仅异常应用送明细；单次报告设 token 上限 |
| 超时降级 | LLM 不可用时（P1 起）自动降级为 P0 模板拼装版日报 |

## 7. 输出（步骤 8）

1. **飞书 webhook 推送**（复用平台现有飞书集成通道）；
2. 可选：创建 `general` 工单归档当日报告（便于检索与复盘引用），该写操作默认关闭。
